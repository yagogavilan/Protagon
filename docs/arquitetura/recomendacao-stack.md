# Recomendação de stack do app real (pré-ADR)

Data: 2026-11-26 · Dono: tech-lead · Status: **recomendação para discussão. Não é ADR e não autoriza início de desenvolvimento.** A decisão só é tomada depois que a diretoria aprovar funcionalidades e visual do mockup (CLAUDE.md §2 e §3). Cada linha "Decidir" abaixo vira ADR nesse momento.

Base: `CLAUDE.md` §3, `docs/00-visao/brief.md` (§3 acesso, §4 telas, §5 Conexões, §7 stack), `docs/design/design-system.md` (F1, F2, F10), `docs/decisoes.md` (D1–D8) e leitura de `apps/mockup/src/lib` e `src/data` (somente leitura).

**O que não foi verificado:** nenhuma documentação de fornecedor (Expo, Supabase, Hotmart, Apple, Google) foi consultada nesta rodada. Tudo que depende de versão, limite, preço ou formato de payload de terceiro está marcado `[HIPÓTESE]` e tem, no fim, um spike ou pergunta para validar. Não há estimativa de custo mensal; qualquer gasto passa pelo fundador.

Nota de coerência: as skills `padroes-backend` e `padroes-mobile` carregadas descrevem outra stack (NestJS, Drizzle, Orval, Next.js). Segui o `CLAUDE.md` (Expo + Supabase). Essas skills precisam ser adaptadas quando o ADR sair (DT a abrir).

## 1. Resumo da recomendação

| Camada | Recomendado | Alternativa principal | Por que esta |
|---|---|---|---|
| App | Expo (React Native, TypeScript strict) + Expo Router, dev build via EAS | PWA reaproveitando o mockup | Push confiável, Live Activity, Wallet e offline de verdade; um código para iOS e Android |
| Backend | Supabase (um projeto de produção, região São Paulo) com Postgres + RLS | NestJS + Postgres próprio | Auth por código, Realtime, Storage e RLS prontos; 1 time pequeno, prazo curto |
| Regras críticas | Funções SQL (RPC) e Edge Functions em TS, **nunca** escrita direta do app nas tabelas de Conexões | Lógica no cliente | Limite diário, visibilidade e consentimento têm que valer mesmo com app adulterado |
| Integrações | Hotmart (webhook + conciliação), import CSV do credenciamento, Wallet | Só lista do credenciamento | Fonte de ingresso confiável e idempotente |
| Admin | Web enxuta (Vite + React + shadcn/ui) sobre o mesmo Supabase | Low-code (Retool etc.) ou Supabase Studio | Time de Eventos opera sob pressão; precisa de guarda-corpos e auditoria |
| Afinidade | Regras por tags no servidor | pgvector/embeddings | Explicável ("motivo em uma linha"), barato, calibrável |

Escopo de v1 sugerido (a validar com o PO): tudo do brief **exceto** Live Activity/widgets, que entram como fase B depois de um spike (seção 2). Motivo: exigem módulo nativo, envio via APNs direto e só existem em iOS.

## 2. App (Expo / React Native)

Risco de aparelho com hora errada, mitigado pelo deslocamento | Alta | Fuso: as 5 cidades usam o horário de Brasília `[HIPÓTESE: confirmar que não haverá edição fora do fuso]`; guardar `timestamptz` UTC e converter só na tela |
| **Escrita offline:** só anotações pessoais (fila local, sincroniza depois). Pedido de conexão, aceite e chat exigem internet | Fila offline para tudo | Evita conflito e duplicidade em regra com limite diário. Custo: botão desabilitado com motivo claro quando sem rede | Alta | UX do "sem internet" precisa de estado em toda ação de Conexões (QA) |
| **Credencial:** QR gerado no aparelho a partir de código opaco do ingresso (não é CPF), brilho máximo (`expo-brightness`), tela ligada | QR rotativo assinado (anti-print) | Opaco é simples e funciona offline. Rotativo evita compartilhar print, mas complica a leitura offline do credenciamento | Média (formato do QR é contrato com o leitor do credenciamento) | Depende de como o credenciamento lê (pergunta 6). | **Push segmentado:** `expo-notifications` + Expo Push Service; tokens em tabela `device_tokens`; **audiência resolvida no servidor** (edição, ingresso, setor, perfil de Conexões ativo) no momento do envio | FCM/APNs direto; OneSignal; tópicos FCM | Resolver no servidor acompanha upgrade e pausa de perfil sem reinscrever tópico. Expo Push poupa configurar APNs/FCM à mão. Custo: intermediário (dados transitam fora do Brasil) | Média: trocar de provedor mexe em um adaptador de envio | Limite de vazão e formato de recibo `[HIPÓTESE]`. Conteúdo do push **genérico** (sem nome de pessoa na tela bloqueada). Android 13+ pede permissão em tempo de execução; D1 já define o momento do pedido |
| **Regra de silêncio no servidor:** notificação tem categoria; só `operacional` sai durante palestra; o resto fica na fila até o intervalo (agenda decide) | Regra só no app | Mesma regra para push e sino; não depende da versão do app | Alta | Agenda atrasada no dia: admin precisa poder "liberar fila agora" (seção 4) |
| **Live Activity / Dynamic Island e widgets (fase B):** exigem **extensão nativa Swift/SwiftUI** (ActivityKit/WidgetKit) via config plugin, ex. `@bacons/apple-targets` ou `expo-live-activity`; módulo Android (Glance) para widget | Notificação local/persistente apenas; só push comum | Dá o "Almoço · retorno 13h30" na tela bloqueada. Custo: código Swift para manter, dev build obrigatório, iOS apenas | Alta (é opcional e isolado) | `[HIPÓTESE]` atualizar com o app fechado exige push `liveactivity` por APNs direto (Expo Push talvez não cubra); limite de duração de uma atividade (cerca de 8 h) é menor que o dia de evento (9h–19h), então reiniciar por bloco; Android tem paridade parcial. **Spike de 3 a 5 dias antes de prometer** |
| **Publicação:** TestFlight/Play interno para homologar; OTA (`expo-updates`) só para JS | Publicar só por loja | OTA permite correção no dia do evento sem fila de revisão | Alta | Revisão das lojas leva dias: congelar versão antes de cada edição. Venda de upgrade dentro do app pode ferir regra de pagamento da Apple (F10) `[HIPÓTESE]` |

Alternativa considerada com mais peso: **PWA** a partir do mockup (Vite + React). Prós: custo menor, sem loja, atualização imediata. Contras: push no iOS exige instalar na tela inicial, sem Live Activity nem Wallet nativo, offline mais frágil, brilho máximo e vibração limitados. Recomendo nativo porque o valor do produto é "ao vivo, na tela bloqueada, sem internet"; a PWA fica como plano B se a diretoria não aprovar contas de loja.

## 3. Backend (Supabase)

| Escolha | Alternativa considerada | Trade-off | Reversibilidade | Riscos |
|---|---|---|---|---|
| **Supabase, 1 projeto de produção multi-edição** (`edition_id` em tudo) + 1 de staging | NestJS + Postgres + Redis (stack do webag); um projeto por edição | Menos peças para operar com time pequeno. Um projeto único permite quem vai a duas edições ter uma conta só. Custo: raio de impacto compartilhado (uma falha derruba todas as edições) | Dados: alta (Postgres padrão, dump). Auth, Realtime, Edge Functions: média (reescrita de adaptadores) | Limites de plano e de conexões em pico `[HIPÓTESE]`; regra de negócio presa em RLS/SQL exige disciplina de teste |
| **Modelo de acesso:** pessoa (`auth.users`) 1—N **ingressos** (`tickets`: edição, tier, status, origem Hotmart/lista). RLS lê o ingresso do usuário em tabela, via função `security definer` estável; **não** confia em claim do JWT para o tier | Tier como claim no JWT (mais rápido) | Upgrade no estande vale na hora, sem esperar renovar token. Custo: uma consulta indexada por requisição | Alta | **Maior risco do projeto:** erro de RLS expõe Conexões ao Executivo. Exigir suíte automatizada de RLS (matriz ingresso × tabela × operação) como portão de CI. Views com `security_invoker = true`; `service_role` nunca no app |
| **Conexões separadas em tabelas por sensibilidade:** `connection_profiles` (visível a VIP/Diamond com consentimento ativo, mesma edição, não bloqueado) · `contact_cards` (telefone, e-mail, redes: só com conexão aceita) · `connections`, `requests`, `messages`, `blocks`, `reports` | Uma tabela larga com colunas protegidas | RLS é por linha, não por coluna: separar tabelas é o jeito simples de garantir "contato só após aceite mútuo" (regra 3) | Média (migração com expandir/contrair) | Join descuidado devolve contato antes do aceite: teste de regressão dedicado |
| **Escritas de Conexões só por RPC** (`send_request`, `answer_request`, `dismiss`, `pause_profile`): limite diário (D4: 15 VIP, 25 Diamond, QR presencial não conta) contado em America/Sao_Paulo, "Agora não" volta no dia seguinte (D5), remetente enxerga "Pendente" nunca "Recusado" | `insert` direto com policy | Regras de produto ficam no servidor e testáveis em SQL | Média | Limites de D4 são "proposta": parametrizar por tabela de config, não em código |
| **Realtime:** **Broadcast** por canal privado da edição (avisos, "Agenda atualizada") disparado por trigger; chat entre dois usuários por Postgres Changes sob RLS | Postgres Changes para tudo; polling | Changes avalia RLS por assinante e escala mal para "todos na sala"; Broadcast é o caminho para fan-out `[HIPÓTESE: confirmar na documentação e em teste de carga]`. **O app deve estar correto sem Realtime**: contador `content_version` da edição + busca ao abrir/voltar ao foco | Alta | Pico às 9h e em cada intervalo (milhares de aparelhos). Teste de carga antes do primeiro evento |
| **Agenda como snapshot publicado:** ao "Publicar" no admin, gera JSON versionado da edição em Storage (CDN) e incrementa `content_version`; o app baixa o arquivo | Cada aparelho lê tabelas do Postgres | Leitura em massa não toca o banco; o mesmo arquivo alimenta o offline | Alta | Etapa extra de publicação; prever "publicar de novo" idempotente. Se a escala real for pequena (centenas), pode-se adiar `[HIPÓTESE]` |
| **Login por código só para compradores:** cadastros criados na importação/webhook; **signups públicos desligados**; app chama Edge Function `request-code` (e-mail ou CPF) que consulta `tickets` e, se existir, aciona o OTP de e-mail do Supabase Auth (6 dígitos). CPF → busca por HMAC; código vai ao e-mail cadastrado (mostrado mascarado) | Auth próprio com SMS/WhatsApp; senha; magic link | Sem senha, como no brief. E-mail é grátis; SMS/WhatsApp custa e depende de provedor. Custo: precisa de SMTP próprio (o padrão do Supabase é limitado) `[HIPÓTESE]` | Média | Enumeração de CPF/e-mail pela mensagem "ingresso não encontrado" (exigida pelo brief): mitigar com rate limit por IP/aparelho e captcha invisível. Força bruta de 6 dígitos: limite de tentativas e expiração curta. Sessão em `expo-secure-store` (valores grandes exigem o padrão de armazenamento criptografado + AsyncStorage). Aparelho offline não pode deslogar |
| **Storage de materiais:** bucket privado; URL assinada de curta duração emitida por Edge Function que confere ingresso e `release_at` ("libera às 14h" decidido pelo servidor, não pelo relógio do aparelho); app baixa para o disco (estado "baixado") | Bucket público com nome difícil | Controle de liberação e revogação. Custo: uma função por download | Alta | **Vídeo** não deve ficar no Storage (custo de saída e streaming): usar Mux, Cloudflare Stream ou similar `[HIPÓTESE: custo a cotar]`. Conteúdo protegido contra repasse? (pergunta 9) |
| **Prévia borrada do cadeado gerada no servidor:** ao ativar perfil com consentimento, uma função gera miniatura minúscula (ex. 24 px) já borrada, guardada em bucket separado; o Executivo recebe só um conjunto pequeno dessas miniaturas, **sem nome, empresa ou id da pessoa**, e o contador vem de RPC que devolve só um número (esconde abaixo de 20, como no mockup) | Blur em CSS/RN no cliente (reversível, F2); só silhuetas genéricas | Irreversível por construção (perde-se a informação antes de sair do servidor). Custo: etapa de processamento de imagem | Alta | Processamento de imagem não roda bem em Edge Functions `[HIPÓTESE]`: pode precisar de um worker pequeno (Node + sharp). **Uso da foto na prévia é finalidade distinta: exige linha própria no consentimento** (seção 6). Se a LGPD pesar, trocar por silhuetas genéricas sem perder o contador |
| **Observabilidade e métricas:** Sentry (RN e funções), logs sem PII; métricas do brief derivadas das tabelas (aceite, encontros) + tabela `app_events` mínima (login, primeira ação, toque no cadeado, NPS) | PostHog/Amplitude desde o dia 1 | Menos fornecedores recebendo dado pessoal. Custo: dashboards próprios simples | Alta | Sentry com scrubbing de CPF/e-mail; ferramenta de analytics, se vier, entra pelo ADR com `security-engineer` |

| Escolha | Alternativa considerada | Trade-off | Reversibilidade | Riscos |
|---|---|---|---|---|
| **Webhook da Hotmart → Edge Function** que valida o token do cabeçalho (`hottok`, comparação em tempo constante), grava o evento bruto em `webhook_events` com **unique (provider, id do evento)** e responde 200 rápido; processamento assíncrono (fila em Postgres + `pg_cron`) cria/atualiza `tickets` | Processar dentro da requisição; Zapier/Make | Idempotência por constraint, não por memória. Eventos fora de ordem (reembolso antes da aprovação) tratados por máquina de estados por transação. Custo: tabela de fila e job | Alta | `[HIPÓTESE]` formato do payload, eventos (aprovada, cancelada, reembolso, chargeback), política de reenvio e se há assinatura além do token: **validar com um payload real de sandbox**. Payload pode conter CPF: guardar redigido ou criptografado, nunca em log |
| **Conciliação diária** pela API de vendas da Hotmart (compara com `tickets`) | Só webhook | Cobre webhook perdido (indisponibilidade, deploy no meio) | Alta | `[HIPÓTESE]` credenciais OAuth e escopo da API de vendas |
| **Mapa produto/oferta Hotmart → tier** em tabela de configuração por edição | Regra fixa no código | Upgrade e novas ofertas sem deploy | Alta | Upgrade é compra nova ou mudança da mesma? (pergunta 3) |
| **Importação da lista do credenciamento:** upload CSV/XLSX no admin → tabela de staging → relatório (duplicados, CPF inválido, e-mail com erro de digitação, conflito com Hotmart) → aplica de forma idempotente por (edição + chave natural) | Digitar à mão; sincronizar com sistema de credenciamento | Prévia antes de aplicar evita lista errada em produção. Custo: tela de conciliação | Alta | Qual é a fonte de verdade de nome no crachá, setor e tier? (pergunta 4). Comprador ≠ participante (empresa compra 5 ingressos com 1 e-mail) |
| **CPF: não guardar em claro.** Armazenar `HMAC-SHA256(CPF, pepper)` para busca de login, os 2 últimos dígitos e a máscara para exibição. Pepper em segredo da função, fora do banco | CPF criptografado em coluna; CPF em claro | Minimização (LGPD). Se o hash vazar sem o pepper, o espaço de CPFs (pequeno) seria quebrável: por isso o pepper é obrigatório. Custo: não dá para recuperar o CPF depois; reimportar da lista se um dia precisar | Média (não se desfaz a perda do dado, mas dá para reimportar) | Se o credenciamento ou nota fiscal exigir CPF completo, rever |
| **Wallet:** Google via link "Save to Google Wallet" (JWT assinado por conta de serviço; abre com `Linking`, sem módulo nativo); Apple via `.pkpass` assinado no servidor, aberto por link/`PKAddPassButton` | Só credencial dentro do app | Wallet funciona offline no próprio sistema, mas exige certificados (Pass Type ID) e aprovação de emissor no Google `[HIPÓTESE: prazo]`. Atualização do passe (Apple) exige serviço web e APNs | Alta (é opcional) | Assinar `.pkpass` pode precisar de worker Node. Passe estático em v1; sem atualização |
| **Admin web enxuto** (Vite + React + shadcn/ui + Supabase Auth com MFA e papéis em `staff_roles`): publicar aviso (público: tudo / ingresso / setor; categoria; agendar), editar horário de sessão (gera "Agenda atualizada" + push), "liberar fila agora", importar lista, ver contadores. Trilha de auditoria (quem, quando, de/para). Guarda-corpos: confirmação com prévia da audiência e contagem, alerta acima de N avisos por hora (reclamação nº 1 do brief: notificação demais) | Supabase Studio; low-code (Retool, Appsmith); Refine/React-admin | Studio não dá guarda-corpos nem auditoria. Low-code acelera, mas custa por usuário e é mais um fornecedor com dado pessoal. Aqui sim os componentes web do mockup (shadcn, tokens) ajudam | Alta | Operação no dia, no celular e em 4G: tela responsiva e simples. **Quem publica avisos ainda é decisão em aberto da diretoria** (brief §8) |

## 5. Afinidade (regras por tags antes de pgvector)

| Escolha | Alternativa considerada | Trade-off | Reversibilidade | Riscos |
|---|---|---|---|---|
| **Cálculo no servidor** (RPC `suggestions`) com a regra do mockup: interesses em comum × 2 + objetivos complementares × 3; níveis "alta" (≥ 9) e "boa" (≥ 5); abaixo de "boa" não sugere; ingresso não altera a ordem (F5). Servidor devolve dados estruturados (interesses em comum, par de objetivos), o app monta a frase | Cálculo no cliente, como o mockup | **O mockup recebe o pool inteiro no cliente** (`rankSuggestions(me, participants)`): no app real isso permitiria raspar todos os perfis. Servidor entrega só uma página de sugestões | Alta | Pesos e cortes (9 e 5) são heurística do mockup, sem dado real `[HIPÓTESE]`: registrar sugestão exibida, pedido e aceite desde o primeiro evento para calibrar |
| **Interesses de lista fechada** (taxonomia de ~40–60 itens + segmento) | Texto livre | Sobreposição de tags só funciona com vocabulário controlado | Média (mudar a taxonomia exige migrar perfis) | Taxonomia é decisão do PO/Design; texto livre quebra a regra |
| **pgvector só depois** | Embeddings desde o início | Tags dão "motivo em uma linha" de graça e são explicáveis; embeddings não explicam. Escala (centenas a poucos milhares por edição) cabe em SQL com arrays `[HIPÓTESE: confirmar tamanho]` | Alta | Gatilho para reavaliar: bio em texto livre entra no produto, ou taxa de aceite fica baixa após calibrar as regras com 1 edição |
| **Pré-cálculo** por usuário ao ativar/alterar perfil e a cada hora; filtros de já respondido, bloqueado, pausado, já conectado | Calcular a cada abertura | Resposta rápida no pico do intervalo | Alta | Cold start: poucos perfis ativos; reaproveitar o corte "mínimo 20" para o contador |

## 6. LGPD (esboço técnico; o parecer é do `security-engineer`)

| Tema | Recomendação | Riscos / a decidir |
|---|---|---|
| CPF mascarado | App nunca recebe CPF completo; API devolve só `cpf_masked`; logs sem CPF/e-mail | Ver CPF em HMAC (seção 4) |
| Consentimento | Tabela `consents` por finalidade, versão do texto, data e origem. Finalidades separadas e desligadas por padrão: (1) aparecer nas Conexões, (2) foto borrada na prévia para quem não tem acesso, (3) liberar contatos após aceite mútuo. **Uso dos dados para marketing/leads do Olimpo é finalidade à parte, nunca agrupada** | Jurídico define bases legais e textos |
| Revogação | "Pausar perfil" e revogar (1) ou (2) tiram a pessoa do pool e apagam a miniatura de prévia imediatamente (efeito pela RLS, não por job) | Conexões já aceitas: o que acontece com o contato já compartilhado? |
| Exclusão ("excluir meus dados") | RPC cria pedido; job remove perfil, conexões, mensagens, notas, tokens de push; mantém só o mínimo do ingresso, anonimizado, quando houver obrigação legal | Backups com ponto de restauração mantêm o dado até vencer a janela: documentar. Prazo de resposta: **verificar com jurídico** |
| Retenção | Chat e Minha rede por 90 dias após o evento (D7), purge por `pg_cron`; exportação liberada no dia seguinte | Exportar contatos de terceiros para fora do app: **verificar** com security |
| Transferência internacional | Supabase em região São Paulo `[HIPÓTESE: disponível no plano]`. Expo Push, APNs/FCM, Sentry e e-mail transacional ficam fora do Brasil: push genérico, sem dado pessoal no corpo | Registrar operadores e cláusulas; RIPD (relatório de impacto) recomendado para Conexões |
| Segredos | Chave `service_role`, pepper, token Hotmart, certificados Wallet, chaves APNs só em segredos das funções/CI, nunca no app (tudo no app é público) | Rotação definida no ADR |
